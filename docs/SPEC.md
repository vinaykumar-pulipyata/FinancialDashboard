# FinancialDashboard: Specification

Status: living document. Update it whenever a decision changes, and add a line to the Change log.

## 1. Overview

A personal finance app. One user, INR only, one password (section 2). It tracks accounts (cash, bank, digital wallets, goal funds, investments, gold, jewellery, debts, receivables, credit cards, property, vehicles), records every transaction, and shows a dashboard of seven views (Calendar, Transactions, Budgets, Spending Review, Stats, Accounts, Net worth) with the diary Notes and your Reminders in the sidebar. It also sets monthly spending budgets and reviews spending against the month before. All data is stored in H2. Excel is a report you can download, not a way to restore; backups (section 4a) are.

| Users | Single user (`admin`), one password set in the app on first run and stored as a BCrypt hash; HTTP Basic, localhost only |
| Storage | H2 file-based: `jdbc:h2:file:./data/financialdb`; the schema is built by Flyway migrations (`src/main/resources/db/migration`) and Hibernate only validates it (`ddl-auto=validate`). Keep `./data` out of git. |
| Excel | Export as a download (Apache POI). A report, not the database and not a backup. |
| Currency | INR only |
| Live prices | Skipped. Investment, gold and asset values are entered by hand. |
| Stack | Spring Boot 4.1.1 (`spring-boot-starter-webmvc`), Java 17, JPA, static `Dashboard.html` served at `/` |
| Packages | `controller`, `service`, `repository`, `model`, `config`, `startup` and `exception` under `com.learning.spring.financialdashboard` |
| Dashboard | Seven view tabs on one card that turns over (Calendar, Transactions, Budgets, Spending Review, Stats, Accounts, Net worth); Notes and Reminders are in the sidebar's Organiser group; a Coming up bar (bills, reminders, recurring, budgets, done recently) sits above the card |

| Spending maths | Spending review (biggest expense, transaction counts, spending observations) and budgets are worked out in the browser from the loaded transactions (expenses, Loans Given left out); the server stores only the budget limits |

## 3. Data model

### 3.1 Account

| Field | Notes |
|---|---|
| id | |
| name | Unique within the same parent |
| type | One of the 13 account types (3.2). Can be changed later only on the same side (asset or debt) and never to or from Receivables, Jewellery or Credit Card, which are created as such; there is at most one Receivables and one Jewellery account. |
| level | Dashboard display tier. Not the hierarchy. Defaults from the type, and can be overridden per account. |
| parent_id | Hierarchy. Empty for a top-level account. No self-parent and no loops. |
| opening_balance | Defaults to 0 |
| target_amount | Optional, mainly for Goal Funds |
| active | Defaults to true. Deactivate instead of deleting when history exists. |
| notes | |

### 3.2 Account types and default levels

| Level | Tier | Types |
|---|---|---|
| 1 | Liquid money | Cash, Bank, Wallet |
| 2 | Goals | Goal Fund |
| 3 | Investments | Investment, Gold, Jewellery |
| 4 | Fixed assets | Property, Vehicle |
| 5 | Money owed to you | Receivable |
| 6 | Liabilities | Debt, Credit Card |
| 7 | Uncategorised | Other |

Assets: Cash, Bank, Wallet, Goal Fund, Investment, Gold, Jewellery, Property, Vehicle, Receivable. Liabilities: Debt, Credit Card. Liabilities are stored as positive amounts owed and subtracted in net worth.

Currency (added 2026-11-16, migration V10). `account.currency` is INR, USD, EUR, GBP or VND (`Currency` enum; the front end's `CURRENCIES` in `core/constants.js` is the same list), INR for every account that existed. Only Cash, Bank, Wallet, Investment, Property, Vehicle and Other can be foreign: goal funds, Jewellery, Receivables, Debt and Credit Card are rupees only for now, and so are the Ledger, Mutual Funds and Shares (their own screens have no currency). A foreign account needs an exchange rate first. Its balance (`balance`) is in its own currency and `balanceInr` is the same amount at today's rate; the net worth sum, the level tiles and the net worth history add up `balanceInr` (the history uses the rate of each month's end, today's for the current month). The currency cannot change once an account has transactions. Transactions on a foreign account are allowed (step 2, see the change log 2026-11-16): `amount` and `fee` are in the currency of the account they belong to (the to-account for an income, the from-account otherwise), and a transfer between two currencies also stores `to_amount` (migration V11, `Transaction.toAmount`, `TransactionData.toAmount`, `Transaction.receivedAmount()`), what arrived in the to-account's currency; it is required then, and refused when the currencies are the same (unless equal, when nothing is kept) or on an income or expense. Loans (Loans Given / Collected) and payments towards a loan or card are rupees only (`TransactionService.checkCurrencies`), and so are the Ledger, portfolio and Jewellery source accounts. Incoming sums everywhere use `coalesce(to_amount, amount)`. Stats, Budgets, Spending Review, the Calendar totals and the Monthly / Income & Expenses export sheets still count rupee transactions only: converting foreign ones at the rate of their day is the next step. An amount in VND is a whole number (`Currency.requireScale`); a rate is rupees per 1 unit with up to 8 decimals (`exchange_rate.rate` NUMERIC(19,8), so 1 VND = 0.0033 keeps its digits), one row per currency and day, entered by hand (menu > Data > Exchange rates, `/api/exchange-rates`: GET, PUT upsert, DELETE; the last rate of a currency an account uses cannot be deleted). The rate used on a day is the latest one on or before it, else the earliest.

### 3.3 Category

| Field | Notes |
|---|---|
| id | |
| name | Unique within its parent |
| kind | INCOME or EXPENSE. Transfers have no category. |
| parent_id | Empty for a category. Set for a sub category. Two levels only. |
| active | |
| system_key | Set only on the fixed categories (Loans Given, Loans Collected, Liability Payments); they cannot be renamed, deactivated or deleted |

Rules:
- A sub category has the same kind as its parent.
- Users can add, edit and delete categories.
- Renaming is always allowed. Changing `kind` is blocked once it has transactions.
- Deleting a category with transactions is blocked. Deactivate it, or reassign its transactions first.
- The starter list (section 6) loads only when the table is empty.

### 3.4 Transaction

| Field | Notes |
|---|---|
| id | |
| date | The date the money moved. It can be in the past. |
| kind | INCOME, EXPENSE or TRANSFER |
| from_account_id | Empty for income |
| to_account_id | Empty for expense, except a Liability Payments expense, where it is the loan or card being paid |
| amount | Greater than 0, in INR. The kind gives the direction. |
| category_id | Optional. Must be empty for transfers. The kind must match. |
| fee | Optional, transfers only: what the transfer cost, charged to the from-account |
| borrower_id | Required on Loans Given and Loans Collected: the person (`borrower`) |
| tags | Up to 10 short lower-case labels in the `transaction_tag` table (transaction_id, tag; migration V9; tag rules as for diary tags, 30 characters). Worked out by `TransactionTagService` when the request leaves `tags` out, otherwise exactly the cleaned list sent. See 3.4a. |
| holding_id | Set on a dividend: the share it came from |
| note | Short text shown as the headline in lists |
| description | Free text. Its words feed the tags (3.4a). |
| created_at | |

Stored in the table `financial_transaction`.

Rules:
- Income needs only a to-account. Expense needs only a from-account. Transfer needs both, and they must differ.
- The one exception: an expense in the fixed category **Liability Payments** needs both. It is paid from an ordinary (non-liability) account into a Debt or Credit Card account, and no other category takes a to-account.
- Transactions can be edited and deleted freely.
- Posting to an inactive account is rejected, and so is changing or deleting a transaction that already uses one (it has to be activated first; 2026-11-19), and editing the account itself.

### 3.4a Transaction tags

- **Order.** From the note and description (at most 3): learned phrases (a hyphenated tag already in use whose words appear in the text) and names written with capitals ("Barbeque Nation" becomes `barbeque-nation`) first, then words used as tags before (most used first), then the other meaningful words (3 letters or more, not numbers, not in the stop list); then, while the transaction has fewer than 3 tags, the sub category name, then the category name.
- **Saved.** A request with `tags` left out (null) gets the worked-out tags, on create and on update; a request with a list gets that list, cleaned and de-duplicated (an empty list means none; more than 10 or a bad tag is refused without quoting the tag). The form sends the list only when a person changed the tags; a transaction being edited keeps its saved tags unless Suggest is pressed.
- **Services that write transactions themselves** (Ledger, portfolios, jewellery) call `TransactionTagService.tag(t)` before saving. `TransactionTagBackfill` tags the transactions that existed before V9 once (oldest first, so early phrases help later ones); the flag `transaction.tags.backfilled` in `app_setting` stops it running twice, so tags removed by hand stay removed.
- **API.** `POST /api/transactions/suggest-tags` `{categoryId, note, description}` returns the list a transaction like that would get (nothing is saved); the Transaction JSON carries `tags`.
- **Page.** Pills under the note in `txnRowElement` (a pill calls `showTransactionsTagged`), tags in the search haystack, a Tags column in the CSV and in the Excel Transactions sheet, the tag box in the transaction form (`transaction-tags.js`).
- **Tag row.** `#txnTags` above the list (`renderTxnTagBar`): the 20 most used tags among the transactions that pass the kind chip, the range and every filter except the tag, each with its count, "+ N more" for the rest; choosing one sets `txnQuery.tag` (an exact tag filter, separate from the search words; Clear and `showTransactionsFor` reset it), choosing it again clears it. A pill on a row and the Calendar day call `showTransactionsTagged`, which sets the same filter.
- **Not done.** Renaming a tag everywhere, tags on the Pay window's liability payments by hand (they are tagged automatically).

### 3.4b Split expenses (added 2026-11-25, migration V17)

An ordinary expense can be shared with people from the Receivables list (`borrower`). Two new tables, no existing row touched:

| Table | Fields |
|---|---|
| transaction_split | What one other person owes of an expense: transaction_id, borrower_id, share (NUMERIC(19,2)); primary key (transaction_id, borrower_id). `Transaction.splits` (a Map, EAGER + SUBSELECT) is its JSON `splits: {"<person id>": share}`. |
| split_settlement | Part of a payment that cleared one person's share of one expense: id, borrower_id, expense_transaction_id, income_transaction_id, amount. The payment is an ordinary Loans Collected income (`SplitService.settle`), so no balance rule is special. |

Rules: the expense keeps its full amount; the user's own share is the amount less the shares. Only an ordinary expense paid from a rupee account can be split (not Loans Given, a liability payment, income, a transfer or a foreign account); every person must exist, each share is more than zero with at most 2 decimals, and the shares cannot add up to more than the amount (the form shares equally, by amount or by percent, in paise, the odd paise staying with the user). What a person owes = opening + given + shared - collected - written off, and the Receivables total adds all shares. A payment clears the person's oldest open shared expenses first, or the `expenseIds` given, and cannot be more than what is open. Once part of an expense is settled its amount and shares cannot change and it cannot be deleted; a payment that settled shares cannot be edited (delete it and settle again, which frees the shares); a person with shares cannot be removed. Stats, Budgets, Spending Review, the Calendar totals and the Transactions found-totals count the user's own share (`rupeeTransactions()`); the transaction list shows the full amount with "your share" and "Split with ..." lines. API: `splits` on `POST/PUT /api/transactions`, `GET /api/splits`, `POST /api/borrowers/{id}/settle-splits` (`{date, toAccountId, amount, expenseIds?, note?}`), `shared` on each person in `GET /api/loans`.

### 3.4c Expenses somebody else paid (added 2026-11-25, migration V18)

`financial_transaction` gets two nullable columns, `paid_by_borrower_id` and `own_share` (no existing row changes). An EXPENSE with a payer has no `from_account_id` (no balance moves), `amount` is the whole bill and `own_share` is what the user owes of it (more than zero, at most the bill; it cannot also be split). Reports count `own_share`; the list shows the bill with "paid by NAME" and "your share". What you owe a person is `sum(own_share) - what you paid back`, **kept apart** from what they owe you: it is `youOwe` on each person in `GET /api/loans`, shown as its own "You owe people" line (Receivables list) and a grey "You owe people (not counted)" line under the net worth sum, and it is never taken off `owed`, the Receivables total or net worth. Paying back (`POST /api/borrowers/{id}/repay-splits`, `{date, fromAccountId, amount, expenseIds?, note?}`) saves a Loans Given expense and `split_settlement` rows (oldest bill first or the ones chosen, at most what is open); a Loans Given with such rows is not counted as lending (`LoanService.summary`, `AccountService.listSummaries`). A bill with a payment against it cannot be changed or deleted, a payment that cleared bills cannot be edited, deleting it frees the bills, and a person with bills cannot be removed.

### 3.5 Balances

Balance = opening_balance + income + transfers in - expenses - transfers out.

A parent account's roll-up is its own balance plus the roll-up of its children. Whether inactive children count is an open question (section 8).

### 3.6 Detail tables

Each links to one account by `account_id`, and only the matching type has a row.

| Table | Fields |
|---|---|
| credit_card_detail | account_id (primary key), credit_limit, due_day (optional, 1 to 31; a short month uses its last day), statement_day (optional, 1 to 31, same rule; added by migration V2) |
| debt_detail | account_id (primary key), emi_amount. A row marks a DEBT account as a **fixed** loan paid in a monthly EMI; a DEBT account with no row is **custom** (paid in any amounts) |
| vehicle_detail | account_id (primary key), number_plate, year_bought, value_updated_on (when the value was last set) |
| emergency_fund_detail | The row marks an account as the Emergency Fund (at most one). target_mode (MONTHS or AMOUNT), target_months, target_amount, monthly_essential_expenses (burn rate), planned_monthly_contribution (optional) |
| borrower | A person you have lent to: name, opening_amount. One list serves both Loans Given and Loans Collected. |
| ledger_detail | A row marks an account as the Future Expenses Ledger (at most one): account_id |
| ledger_bucket | A bill the Ledger saves for: name, monthly_allocation, payment_amount (the bill and the target), frequency_months, next_payment_date, previous_payment_date, end_date, is_buffer, closed_at |
| ledger_entry | Every change to a bucket's balance, signed: bucket_id, date, kind (OPENING, ADJUST, INTEREST, FUND, PAY, MOVE_IN, MOVE_OUT, CLOSE_OUT, CLOSE_IN), amount, note, transaction_id |
| ring_fence | A row means the goal fund is ring-fenced: account_id (primary key), fenced_at (stored, not shown) |
| portfolio_detail | A row marks an account as the Mutual Funds or Shares portfolio (one each): account_id (primary key), kind (MUTUAL_FUNDS or SHARES), total_invested |
| holding | One fund or share in a portfolio: id, account_id, name, invested_amount, current_value, quantity (units or shares, optional, 4 decimals; migration V5). The portfolio's balance is the sum of its holdings' current values. |
| holding_snapshot | A holding's figures on a day, saved on add, update and withdraw for the Stats graphs: id, holding_id, account_id, date, invested_amount, current_value |

- The amount owed on a debt or card comes from the transactions. There are no principal, interest or EMI fields: an EMI is an ordinary transfer to the debt.
- Investment, gold, property and other asset accounts hold their value as an ordinary balance (opening balance and transactions); Mutual Funds and Shares are the exception (`portfolio_detail`, `holding`). The earlier plan for `investment_detail`, `gold_detail`, `debt_detail`, `receivable_detail`, `asset_detail` and `value_history` tables was not built.
- Future Expenses Ledger (one real account, type Goal fund, named "Future Expenses Ledger", created by Set up; at most one). The money sits in that account; its buckets are slices tracked in `ledger_bucket` and `ledger_entry`. A bucket's balance is the sum of its entries, so history is never deleted; the buckets always add up to the Ledger's balance. There is no "unallocated money": anything that belongs to no particular bill lives in the Buffer. Bucket fields: name, monthly allocation, bill amount (also the target: "Funded" once the balance reaches it, otherwise "Short by X"), how many months between bills (any whole number from 1 to 120; 1 is monthly, 3 quarterly, 12 yearly) together with the next payment date (both or neither), previous payment date (optional when adding or editing, for a bucket that already has history; set by the app on each payment; it cannot be in the future), optional end date, and a buffer flag that only the default Buffer has. Every Ledger starts with a default bucket called Buffer (monthly allocation 0, no bill amount, no due date, no end date, marked as the buffer). The buffer is only ever this default bucket: there is no option to mark another bucket as the buffer. It can never have a bill amount, payment dates or an end date (the server refuses, and the Edit dialog switches those fields off for it), because an end date could block funding and the buffer cannot be closed.  Set up creates it, and at start-up a Ledger that has no buckets at all gets one. The buffer cannot be closed. Due date and target are optional. Buckets are listed by next payment date, soonest first, undated last.
  - **Fund Ledger** is a transfer: pick the source account and the amount (date is today). The amount is confirmed. Exactly the monthly plan (sum of open buckets' allocations): each bucket gets its allocation. Less: the request must say how much each bucket gets, adding up to the amount. More: the extra goes to the Buffer. It records a real transfer into the Ledger account. The source cannot be the Ledger, a receivable, inactive or ring-fenced. With no open buckets Fund Ledger is disabled (and refused by the server), as are Edit, Pay, Transfer and Close. Set up creates the account and its default Buffer and then opens Add bucket straight away. Because the Buffer always exists, cancelling that dialog leaves a normal card showing the Buffer with its buttons (the Set up prompt no longer comes back).
  - **Pay** takes an amount from one bucket (reconfirmed in the dialog). It is refused if the bucket holds less: move money in with Transfer first, so a bucket never goes negative. It records a real expense from the Ledger account with the note "Paid: <bucket>", sets the previous payment date to today and moves the next payment date forward by that many months.
  - **Deleting a funding**: the "Funded the Future Expenses Ledger" rows in the Transactions list have a 🗑 (asks for confirmation). It deletes the transfer and takes back what it added to each bucket, so the Ledger and the buckets return to how they were. It is refused, with a message naming the bucket, if a bucket has already used money from that funding (for example a payment was made). An older funding that put part of its money in no bucket has that part taken back out of the Buffer. Payments and interest cannot be deleted from the list, and nothing about the Ledger can be edited there. API: `DELETE /api/ledger/fundings/{transactionId}`.
  - **Credit interest** records interest the bank paid on the Ledger (usually quarterly; the app does not calculate it): the user types the amount from the statement. It always goes to the buffer, raises the Ledger's total, and is recorded as an income transaction into the Ledger account under Investment Income > Interest when that category exists (uncategorised otherwise), so it shows in the income chart. API: `POST /api/ledger/interest`.
  - **Transfer** moves money from one bucket to another, limited to what the first one holds.
  - **Money held now**: adding a bucket can start it with money the user already has saved (an OPENING entry); editing a bucket shows the money it holds and a different value corrects it (an ADJUST entry). Either way the Ledger account's opening balance changes by the same amount, so the Ledger total includes it and the buckets still add up to it. It cannot be negative. Leaving the field blank when editing changes nothing.
  - **Close** asks for confirmation, and for which bucket what is left goes to (the Buffer by default). That bucket also receives the closing bucket's monthly allocation (added to its own), so the monthly plan stays the same. The bucket gets a `closed_at` date and moves to "Closed buckets" with its history kept. Closing is never automatic.
  - **End date passed**: an open bucket whose end date has passed is flagged, and Fund Ledger is refused until it is closed or its end date is updated (there is no "decide later").
  - The Ledger is used only through its own buttons: it does not appear in the Income, Expense and Transfer forms, the server refuses ordinary transactions to or from it, and its transactions cannot be edited or deleted elsewhere. It cannot be ring-fenced and cannot be the Emergency Fund. Deleting its account removes its buckets and history only if it has no transactions.
  - API: `GET /api/ledger`, `POST /api/ledger/setup`, `POST` and `PUT /api/ledger/buckets`, `POST /api/ledger/buckets/{id}/close`, `POST /api/ledger/fund`, `/pay` and `/transfer`. Each returns the Ledger as it is afterwards.
- Net worth over time: `GET /api/net-worth?months=12` (1 to 60, oldest first) returns, for each month, the net worth at the end of that month (for the current month, every recorded transaction), with the assets and liabilities behind it. `NetWorthService` replays the transactions dated up to that day on top of the opening balances with the same rules as the dashboard balances: assets are opening + in - out, a liability flips the sign, Receivables (money lent) is left out of net worth altogether, and only active accounts count. A transaction dated in the future is counted in the latest point (as the account balances count it) and in no earlier month. Only recorded transactions are replayed: a change in the value of an investment, gold or property is not tracked, so it is not in the chart.
- Receivables and loans: the two fixed categories **Loans Given** (an expense) and **Loans Collected** (an income) are created at every start (`category.system_key`), cannot be renamed, deactivated or deleted, and cannot have sub categories. A Loans Given or Loans Collected transaction must name a person (`transaction.borrower_id`); no other category takes one. The Receivables account's balance is not posted to directly: it is its opening total + all loans given - all loans collected, worked out when accounts are listed. Lending lowers the bank account and raises Receivables by the same amount, so net worth does not change. Each person owes opening amount + given - collected, and may go negative (they paid back more than they owed; the form warns first and then allows it). The part of the Receivables opening total not given to any person shows as "Earlier loans (no name)"; a person's opening amount comes out of it and cannot exceed what is left. The first person or loan creates the Receivables account if there is none. A person with loan transactions cannot be removed. Loans Given and Loans Collected are left out of the income and expense charts and totals. API: `GET /api/loans`, `POST /api/borrowers`, `PUT` and `DELETE /api/borrowers/{id}`.
- Ring-fencing applies to goal funds only: the Emergency Fund and the user's own goals. It does not apply to the Future Expenses Ledger or its buckets, which are a sinking fund (money is collected and paid out). It can be switched on only once the fund has reached its target, never part-way: the Emergency Fund's own target, or a custom goal's `target_amount` (a goal with no target cannot be ring-fenced). While ring-fenced, money can go in but a new expense or transfer out of the fund is refused until it is released (`POST` and `DELETE /api/ring-fences/{accountId}`). An old outflow can still have its note or date edited, but not be made larger. Releasing asks for confirmation. Account summaries carry a `ringFenced` flag. The forms keep a ring-fenced fund out of the "spend from" choices. Deleting the account removes the ring-fence. A fund is not released automatically if its balance later drops below the target.
- Emergency Fund figures are calculated, never stored: target (months x monthly essentials, or the fixed amount), remaining, progress, runway in months (balance / monthly essentials), and the estimated date. The estimate uses the planned contribution when set, otherwise the average money into the fund over the last 3 months (opening balance excluded). API: `GET` and `PUT /api/emergency-fund`. An existing goal fund can be chosen as the Emergency Fund; otherwise one named "Emergency Fund" is created.

### 3.6a Tables not tied to an account

| Table | Fields |
|---|---|

- Jewellery (`JewelleryService`, `/api/jewellery`): the account's balance is what the items cost. Adding an item paid from a bank or cash account is an ordinary transfer in; an item already owned adds its price to the account's opening balance (so net worth history counts it from the start). Editing a price or removing an item moves the opening balance by the difference. Selling (all or part of the weight) is a transfer out of the cost (or its share by weight) to a bank or cash account, plus the difference to the sale price as income (Investment Income) or an expense (Other Expense). Like the Ledger and the portfolios, `TransactionService` refuses ordinary transactions on the account. Every call returns the whole panel.

### 3.7 How transactions map to account types

- **Loan taken:** income to a bank account, and the debt balance goes up.
- **EMI or card bill payment:** the Pay button on the debt or card row records an expense (category Liability Payments) from the bank, with the debt or card as its to-account. It lowers what is owed through the usual rule (money into a liability) and shows in Transactions and the Expenses chart. A transfer to a liability still works and lowers the amount owed too, but it is not an expense.
- **Card purchase:** expense from the card account, which raises the amount owed.
- **Lending:** transfer from bank to the receivable. Repayment is the reverse.
- **Buying an investment or gold:** transfer from bank to the investment account.
- **Digital wallet (PhonePe, Paytm, Amazon Pay):** adding money is a transfer from a bank account to the Wallet account; paying from it is an expense; cashback and refunds are income into it. UPI payments made through a wallet app come from the bank, not the wallet.

## 4a. Backups

The goal is that no data is lost: at most the entries since the last backup (a day, usually nothing), and never silently.

- **What a backup is.** A zipped file of SQL commands (H2 `SCRIPT`) that rebuilds every table and every row, written to `./backups` (next to `./data`). It is a text format, so it survives an H2 upgrade. Names are `backup-YYYY-MM-DD_HHMMSS.sql.zip`.
- **When.** When the app starts, when it is closed, and, if it stays open, whenever an hour passes with no good backup from the last 24 hours. "Back up now" in the Backups popup does one at once.
- **Checked every time.** The file is written under a temporary name, loaded into a throw-away in-memory database, and every table's row count and a SHA-256 of its rows are compared with the live data, which is read in the same snapshot as the copy. Only a matching copy gets its real name; a bad one is deleted and shown as a failure. An earlier good backup is never touched by a failed one.
- **Kept.** The newest backup of each of the last 30 days, and the first backup of every month for ever (`BackupRetention`). The newest is never deleted. Files that are not named like ours are never touched.
- **A second place.** One setting, "Also copy every backup to this folder" (iCloud Drive, Dropbox, a USB drive). It is checked for write access when saved, every backup and report is copied there and the size compared, and the same thinning rule is applied there. The setting and the result of the last backup live in the `app_setting` table.
- **A monthly Excel report** (section 4) is saved as `report-YYYY-MM.xlsx` with the first backup of each month, and copied to the second folder.
- **Warnings.** A red bar at the top of the dashboard when the last backup failed, when there is no backup yet, when the last good one is 2 or more days old, or when the copy to the second folder failed; an amber bar while no second folder is set. Clicking it opens the Backups popup.
- **Restoring.** Close the app and start it once with `--restore=FILE` (`financial-dashboard --restore=FILE`, `scripts/financial-dashboard.sh --restore=FILE`, or `./gradlew bootRun --args='--restore=FILE'`). The backup is first loaded into a new database file next to the real one; only if that works is the current database moved aside as `financialdb.mv.db.before-restore-<time>` (never deleted) and the new one put in its place. A missing, damaged or empty backup stops the start-up and changes nothing.
- **Not covered.** Entries made after the last backup. Backups are not encrypted and hold the password hash, so keep the folders private (FileVault, a protected cloud account).

- `AccountService.update` sets the type from the request unconditionally (`apply`, line 228), so an account can be turned into a Ledger-like, portfolio, card or Receivables account without its detail rows, and the type decides the liability sign. Nothing stops a second RECEIVABLE account either, and only the first active one gets the loans total.
- Reported, consistent with the code read: if the Receivables account is deactivated, `LoanService.findReceivablesAccount` (active only) finds none, tries to create another "Receivables" and the name check refuses it, so a loan cannot be recorded until it is reactivated.
- `PortfolioService.updateValue` sets the holding's current value even when the date is earlier than its newest snapshot, so the balance and the newest stats point can disagree. Reported: the current month's net worth point uses the holdings' value, so an Invest transfer lowers net worth until the new value is entered.
- `NetWorthService.history` clamps to 60 months (5 years): the page and the export ask for 120, so the "All" zoom shows at most 5 years (README said ten).
- `NoteRepository` text search builds `like '%' || :text || '%'` without escaping `%` and `_`, so a search for `100%` or `_` matches almost everything.
- `NoteService.cleanTag` uses `\s` (ASCII) where the browser's `normalizeTag` uses the Unicode `\s`, so a tag with a non-breaking space is turned into `a-b` by the page but refused by the server.
- `EmergencyFundService`: `.intValue()` on remaining / contribution can overflow for a tiny contribution (a 500 from `plusMonths`); progress rounds 99.96% up to 100.0 while `targetReached` is false. `CategorySeeder` brings the starter categories back if every ordinary category is deleted. Reported: `SystemCategories` taking over an ordinary same-name category does not check for sub categories or transactions.
- Reported, backups: the monthly report and the second-folder copy are written straight to their final name (a crash leaves a truncated file that counts as done); `status()` turns an `IOException` while listing into a 500; `BackupRestorer` honours only `--spring.datasource.url=`, not the environment variable, and does not check the database is closed.

Validation and error shape (reported by several readers, and consistent with `ApiExceptionHandler` mapping only `ValidationException` and `NotFoundException`): no length checks on names and notes against the VARCHAR sizes (255, 1000), no scale or size check on amounts (NUMERIC(19,2)), and a bucket name over about 240 characters overflows the 255-character `note` of its own entries. Each of these ends as a database error and a 500 with Boot's default body, not `{"error": ...}`; malformed JSON, enums and dates likewise get Boot's default 400.

Doc drift fixed now: README net worth span (5 years), `AccountService.delete`, the notes `size` rule, the `{"error": ...}` wording, the Flyway properties, and the logging caveat. The gap in section 3.6 (Ledger fund sources) is closed in the code: `LedgerService.fund` refuses a portfolio or Jewellery source.

Not covered by any test (the readers' lists): the encoded-path case for the header filter; month-end `pay` drift; funding from a portfolio account; `deleteFunding` into a closed bucket; amounts with more than 2 decimals or very large; long names; a refusal message containing a name or amount reaching the log; back-dated `updateValue`; more than 60 months of history; a deactivated Receivables account (now covered); changing an account's type (now covered); a wildcard in note search; the Unicode-space tag; `DebtService` on its own (only through `ApiTest`).

- 2026-11-27: Binaries and CI. The project is on GitHub (`vinaykumar-pulipyata/FinancialDashboard`). `ci.yml` runs `./gradlew build` on every push and pull request (one Linux job). `release.yml` runs on a `v*` tag: tests once, then builds a **GraalVM native executable** on Linux x64, Linux arm64, macOS Apple silicon (Intel Macs left out on purpose) and Windows, smoke-tests each with `scripts/smoke-test.sh` and attaches it, with a SHA-256 file, to a GitHub Release (a hyphenated tag is a pre-release). Decisions: native executables (about 190 MB, start in about 4 s, no Java needed) rather than a jar with a bundled runtime, because the native build proved workable on macOS (all 32 smoke checks pass); GraalVM 25 is required (Spring Boot 4's metadata format; GraalVM 24 fails with "Missing attribute(s) [glob]"). What it took: `NativeImageHints` (Hibernate's `*_$logger` classes), a tracing-agent recording of the reflection and resources the app uses (`scripts/native-experiment.sh --agent`, with ByteBuddy's provider removed because Hibernate 7.4 picks its byte-code provider only through the Java service lookup) and `-H:+AddAllCharsets` (Apache POI needs Windows-1252). Version set to `0.1.0`. Not yet done: the release workflow has not run, so Windows, Linux arm64 and the small macOS runner are untested; the files are unsigned (macOS needs `xattr -d com.apple.quarantine`, Windows shows SmartScreen); the first release (`v0.1.0`) is not published. The README, SETUP, OPERATIONS and DEVELOPMENT pages describe all of this.

- 2026-11-27: One-command install. `scripts/install.sh` (macOS and Linux, POSIX `sh`, meant for `curl ... | sh`) finds the system (Linux x64 and arm64, macOS Apple silicon incl. under Rosetta; Intel Macs and other systems are refused), downloads the matching release file and its `.sha256` (from `releases/latest/download`, or `releases/download/<tag>` with `--version`), refuses on a checksum mismatch, installs into `~/.financial-dashboard/` (the folder of the earlier Java-based launcher: `app.jar` and `data/` are kept, an old launcher is saved as `financial-dashboard.previous`), writes a launcher that starts the app from that folder and opens the browser, and links it from `~/.local/bin`. `--uninstall` keeps the data. `scripts/install.ps1` does the same for Windows x64 (into `%LOCALAPPDATA%\FinancialDashboard`, a `.cmd` launcher, the user PATH). The release files stay plain executables (not tar files): a checksum and a copy are all the installer needs. `scripts/test-install.sh` tests the shell installer offline against a fake release and runs in CI. Not yet tried: a real release download, and `install.ps1` on Windows.

- 2026-11-28: First dry runs of the release workflow. `v0.1.0-rc3`: Linux x64, Linux arm64 and Windows built, passed the smoke test and were attached to the pre-release (about 192 to 199 MB each, with SHA-256 files); macOS failed.
