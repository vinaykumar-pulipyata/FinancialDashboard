# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A single-user personal finance app (INR only, one password via HTTP Basic): Spring Boot 4.1.1 (Spring Framework 7, Java 17) with JPA on a file-based H2 database, serving a plain HTML/CSS/JavaScript dashboard from `src/main/resources/static`. `docs/SPEC.md` is the living specification (data model, rules, build order, and a dated change log). Read it before changing behaviour, and add a change-log line when a decision changes. `README.md` is a compact front page (quick start, a one-line list of features that each link to a detail page, and links to the other docs); the details live in `docs/features/*.md` (views, accounts, transactions, people-and-splits, funds-and-investments, budgets-and-review, notes-and-reminders, look-and-feel, security-and-backups, excel-export-import), `docs/SETUP.md`, `docs/OPERATIONS.md` (running, demo data, backups, logs, configuration), `docs/DEVELOPMENT.md` (layout, REST API, tests, limits) and `docs/MONEY-MANAGER-IMPORT.md`. Update the matching detail page when a feature is added, changed or removed, and add a line to the README list only for a whole new feature.

`python3 scripts/import-money-manager.py plan FILE.xlsx` then `... apply` imports an export of the Money Manager app (one sheet: Date, Account, Category, Subcategory, Note, INR, Income/Expense, Tag, Description, Amount, Currency) into a NEW, EMPTY database started with `scripts/financial-dashboard.sh moneymanager` (`./data/moneymanager`, backups in `./backups-moneymanager`). `plan` changes nothing and writes `import-review/` (`account-map.csv` and `category-map.csv` are edited by hand and read back on the next `plan`, `plan.csv`, `rates.csv`); `apply` (password from `FINANCE_PASSWORD`) sets the exchange rates, creates the accounts, creates missing categories (case-insensitive get-or-create, so the starter ones are reused), saves the rows oldest first and sets every opening balance to 0, and **refuses to run if the database has any account or transaction**. While it runs the accounts hold a 10 billion cushion so the funds check never stops a row (credit cards need none); a Money Manager `Loan` > person expense is saved in the fixed Loans Given with that person as a borrower, and a negative one (a repayment) in Loans Collected, so Receivables follows (the first borrower makes the Receivables account; `apply` leaves its opening alone); any other negative expense becomes income (`Refund` > the original category), `Modified Bal.` rows become `Balance correction`, a transfer between two currencies takes the rupee figure from the INR column and what arrived from Amount, and a row in a different currency than its account is converted at that day's rate. `plan` also takes `--until DATE` (with `--extend "HDFC,Cash=2026-10-29"`, those accounts go on to the later day while the others stop at `--until`) and `--from-row N` (the export is newest first, so row N or higher is the oldest part), and reads `import-review/row-overrides.csv` (file_row, action, target, why; actions OPENING, TRANSFER (target `Account` or `Account=amount that arrived` for two currencies), TRANSFER_FROM, PAYMENT into a loan or card, CATEGORY, SPLIT, SKIP, EXPENSE (a transfer row that is really money spent: target `Category > Sub`), OK = reviewed; `category-renames.csv` also takes optional `from_date` / `to_date` columns, so a rename can apply to one trip's days only, which is how Kerala Trip and Vietnam Trip came from Trips), which is also the progress log of the row-by-row review; `account-map.csv` columns `backfill_months`, `backfill_amount`, `backfill_from` (a fund or deposit that was fed every month before the file starts: that many monthly transfers from that Money Manager account, on the day of the month of its first row, going back from it; the source account\'s opening balance rises by the total so its balance on the first day stays what the file says; an `opening_balance` on a fund holding is what it already held, added first, and each monthly Invest into a fund raises its value by what was put in, on that day, so its stats graph follows the invested amount until a sale; a sale larger than the fund\'s worth first sets its value to the sale amount on that day); `account-map.csv` type `HOLDING_RECURRING_DEPOSIT` makes an account a deposit of the Recurring Deposits card (terms in `rd_start_date`, `rd_term_months` (60 is a placeholder), `rd_monthly_amount`, `rd_interest_rate`, `opening_balance` = already deposited; money into it is a dated Deposit, money out of it closes it); optional `budgets.csv` (category, sub_category, amount; empty category = all spending) saves monthly limits and `portfolio-values.csv` (kind, name, current_value, date) sets what a holding is worth on a day, for market values the rows cannot know; optional `notes.csv` (date, title, body, tags separated by `|`) and `reminders.csv` (date, title, repeat, done, done_on, ticked_days `day=done on` separated by `;`) save the dashboard's own notes and reminders through the API; an optional `borrowers.csv` (name, opening_amount: people who already owed you before the first loan row; the Receivables opening becomes their total) and `portfolio-holdings.csv` (kind MUTUAL_FUNDS or SHARES, name, quantity, invested, current_value: holdings that exist only in the dashboard, created through the portfolio API); an optional `extra-plan-rows.csv` (the columns of `plan.csv`, in the app's own names, `file_row` any unique number such as 900000 + the dashboard's transaction id) adds rows that are not in the workbook, such as the transactions of accounts kept only in the real dashboard (renames and `CATEGORY` row overrides apply to them, and they join the rows by date), and `account-map.csv` has optional `target_amount` (goal fund), `due_day` and `statement_day` (card) columns for such accounts; `account-map.csv` type `LEDGER` (the default for "Monthly Expense", app name `Future Expenses Ledger`, which the app fixes) sets up the app's own Ledger and saves each transfer into it as a dated funding (`POST /api/ledger/fund` with the optional `date` of `FundRequest`; the money goes to the Buffer), a bill paid from it is saved as a bucket named after the bill (`LedgerService.PayRequest` has an optional `date`, `categoryId` and `note`: the money moves from the Buffer into the bucket, then it is paid on its day under the row's category) and interest credited to it as `InterestRequest` (optional `date` and `categoryId`); `account-map.csv` type `EMERGENCY_FUND` makes the account the app's own Emergency Fund (created as a goal fund, then set on the Emergency Fund card with a placeholder target of 6 months of 90,000 a month, `EF_TARGET_MONTHS` / `EF_MONTHLY_EXPENSES` in the script); an optional `emergency-fund.csv` (target_mode MONTHS or AMOUNT, target_months, target_amount, monthly_essential_expenses, planned_monthly_contribution) replaces that placeholder with the real card settings, and an optional `ledger-buckets.csv` (name, pays = the Money Manager bill names it pays separated by `;`, monthly_allocation, payment_amount, frequency_months, next_payment_date, previous_payment_date, end_date, balance) makes the Ledger's buckets the real ones: bills are paid from the bucket named in `pays`, and at the end every bucket gets its settings and dates and its `balance` (moved from or to the Buffer, which keeps the rest); `account-map.csv` type `HOLDING_MUTUAL_FUNDS` / `HOLDING_SHARES` makes a Money Manager account a holding inside the app's Mutual Funds / Shares account (set up by `apply`; transfers into it are dated Invest calls, out of it dated Withdraw calls); `account-map.csv` carries `opening_balance` (a loan's amount owed on the first day) and `emi_amount` (a fixed loan), and entries for accounts a narrower plan does not use are kept for a later, wider one; `apply` creates only the accounts the planned rows use and `--clear-starter-categories` first deletes the app's built-in categories. `ImportMoneyManagerTest` runs both steps through `src/test/resources/import_bridge.py` on a workbook it builds. `python3 scripts/load-demo-data.py [--years N]` loads all the demo data through the API in one go, five years by default (accounts, three of them wallets, and about 5,500 transactions (a dining-out surge and a laptop this month and a dental bill last month give the Spending Review view something to find), 2 to 3 on every day plus the monthly ones, the Emergency Fund, goal funds, loans and Ledger, one or two tagged diary notes on every day, random reminders (two to four done a month, two late, others coming up) and twelve special ones that repeat (yearly, monthly, weekly), then mutual funds and shares with a monthly value history and half-yearly dividends; `./Caddyfile` is an optional, project-local proxy (`caddy run --config ./Caddyfile`, not a brew service; `scripts/financial-dashboard.sh` starts it in the background, logs to `logs/caddy/<year-month>/<date>.log`, runs `./gradlew bootRun` in the foreground and stops the proxy on exit; `scripts/financial-dashboard.sh demo` runs on `./data/demo` with backups in `./backups-demo` so demo backups never mix with or prune the real ones, and it prints which database is in use, and falls back to the app alone if Caddy is missing or cannot start) that serves `http://finance.localhost/` on port 80 and forwards it to 127.0.0.1:8080 (it must not `bind 127.0.0.1`: macOS refuses that for port 80 without administrator rights, so it listens on all addresses and a `remote_ip` check answers 403 to anything not from this computer; keep that check); keep it project-local (`admin off`, `auto_https off`) and never write Caddy config outside the project folder. Tests use an in-memory H2 (`src/test/resources/application.properties`), never the real file.

Tests (about 451 Java and 466 JavaScript; `./gradlew test`): service tests are plain `@SpringBootTest` classes (one per service, plus `*ValidationTest` classes for the refusals and edge cases). `ApiTest` drives the whole REST API through `MockMvcBuilders.webAppContextSetup(...)` from spring-test with the `springSecurityFilterChain` added as a filter, so security, JSON and the error handler are covered without opening a port. If Gradle will not start in a sandbox (it needs a local socket), the suite can still be compiled with `javac` and run with the JUnit Platform launcher: the classpath is the jars inside an installed `app.jar` (`BOOT-INF/lib`) plus JUnit 6, AssertJ, Mockito, `spring-boot-test`, `spring-boot-test-autoconfigure` and `spring-test` from `~/.gradle/caches`, and JaCoCo's agent measures coverage. ## Back end

Layers under `com.learning.spring.financialdashboard`: `controller` (thin REST, `/api/...`), `service` (all rules), `repository` (Spring Data), `model` (entities), `startup` (runners), `exception` (`ValidationException` becomes 400 and `NotFoundException` 404, both returned as `{"error": "..."}` by `ApiExceptionHandler`, and the front end shows that message as is).

Things that need several files to understand:

- **Balances are calculated, never stored.** `AccountService.listSummaries()` returns `AccountSummary` with `balance` = opening balance + money in - money out. For a liability (debt, credit card) the balance is the amount owed, so the sign flips. `Account.level` is only the dashboard tier; hierarchy is `parentId`.
- **Detail tables mark special accounts.** A row in `emergency_fund_detail`, `ledger_detail`, `portfolio_detail`, `ring_fence`, `vehicle_detail` (also holds when a vehicle's value was last set, which `AccountService.create/update` maintain) or `credit_card_detail` (primary key = account id; columns `credit_limit`, `due_day` and `statement_day`, the last two optional and different days) is what makes an account the Emergency Fund, the Ledger, a ring-fenced fund, or a card with a limit. Services ignore a detail row whose account no longer exists. `AccountService.delete` cleans these up, except `credit_card_detail`, whose row is left behind (harmless).
- **Account types are guarded.** `AccountService.create` allows at most one RECEIVABLE and one JEWELLERY account (`requireOnlyOne`; the wizard, `LoanService.ensureReceivablesAccount` and `JewelleryService.setUp` all create through it, and a switched-off Receivables account makes `ensureReceivablesAccount` say so). `update` refuses (`requireTypeChangeAllowed`) a change to or from RECEIVABLE, JEWELLERY or CREDIT_CARD (they need their own details), between an asset and a liability (the sign of the whole history would flip) and for a goal fund with an Emergency Fund or ring fence; `requireManagedFieldsUnchanged` still protects the Ledger, portfolios and Jewellery. Same-side changes (Cash, Bank, Wallet, Investment, Property, Vehicle, Other) are allowed.
- **`SetupService`/`/api/setup/accounts` is the single batch endpoint for creating accounts** (used by the wizard and the per-level Add popup). It handles the credit-card limit (required), a fixed loan's `emiAmount` and names the Receivables account automatically.
- **Currency.** INR is the base. `account.currency` (`Currency` enum: INR, USD, EUR, GBP, VND with `decimals`; `CURRENCIES` in `core/constants.js` is the same list, change both) and `exchange_rate` (rupees per 1 unit, NUMERIC(19,8), one row per currency and day; `ExchangeRateService`, `/api/exchange-rates`; `table().on(currency, day)` gives the latest rate on or before a day, else the earliest) come from `V10__currency.sql`. `AccountSummary` has `currency` and `balanceInr` (today's rate); the front end adds up `balanceInr(a)` (`util.js`; falls back to `balance`) for the net worth sum and level tiles, and `NetWorthService` converts each account at the rate of the month's end; keep these in step. Only BANK, CASH, WALLET, INVESTMENT, PROPERTY, VEHICLE and OTHER can be foreign (`AccountService.RUPEES_ONLY`, `CURRENCY_TYPES` in constants.js); a foreign account needs a rate, whole numbers for VND, no currency change once it has transactions, and an update with no `currency` keeps the account's own. **Transactions on a foreign account are allowed**: `amount` and `fee` are in the currency of the account they belong to (`txnCurrency(t)` in `core/currency.js`), and a transfer between two currencies also carries `toAmount` (V11, `Transaction.receivedAmount()` = `toAmount` or `amount`; `TransactionService.checkCurrencies` requires it then and refuses it otherwise, checks decimals per currency, and keeps loans and loan or card payments in rupees; `LedgerService.fund`, `PortfolioService`/`JewelleryService.requireBankOrCash` want a rupee account). Every sum of money coming into an account must use `coalesce(to_amount, amount)` / `receivedAmount()` (the repository queries, `NetWorthService`, `balanceAfter`); keep them in step. **Stats, Budgets, Spending Review, the Calendar totals, budget alerts and the Transactions found-totals add up rupees through `rupeeTransactions()` / `toRupees(t)` (`core/currency.js`): a foreign income or expense is counted at the rate of its day (`rateOn`), a transfer touching a foreign account and anything with no saved rate are left out, and the `.foreign-note` shows only while some foreign income or expense has no rate; any new analytic code must use them. The Monthly / Income & Expenses export sheets still add `amount` as rupees and leave foreign rows out.** `rateOn(code, day)` (page state `exchangeRates`) pre-fills a transfer's received amount. `inCurrency(n, code)` formats an amount in its own currency. `AccountData` and `SetupAccount` have an 8th / 13th `currency` component with the old constructors kept.
- **Receivables are derived.** The Receivables account's balance is its opening total + all Loans Given - all Loans Collected, added in `AccountService.listSummaries`. Loans Given (expense) and Loans Collected (income) are fixed categories (`SystemCategories`, `category.system_key`, protected from edits), and a transaction in them must carry a `borrowerId` from one shared `borrower` list (`LoanService`). `CategorySeeder` (order 1) must run before `SystemCategoryInitializer` (order 2).
- **Expenses split with people** (`V17__expense_split.sql`, `TransactionData.splits`, `SplitService`, `SplitController`, `core/split-calc.js`, `panels/split-form.js`, `panels/split-block.js`): an ordinary expense paid from a rupee account can carry `splits` = what each *other* person (a `borrower`, the Receivables list) owes of it; the user's own share is the amount less these, and the expense keeps its full amount (balances and net worth are unchanged, so no special case). Shares live in `transaction_split` (an `@ElementCollection` Map on `Transaction`, EAGER + SUBSELECT like tags; JSON `splits: {"7": 295}`), and add to the Receivables total (`AccountService.listSummaries`) and to each person's `owed` (`LoanService.BorrowerView.shared`; owed = opening + given + shared - collected - written off). `TransactionService.checkSplits` refuses a split on anything but an ordinary expense, on a foreign account, an unknown person, a non-positive share or shares above the amount; `null`/empty = not split, so every update must send the existing `splits` again (the form does). **Settling** (`POST /api/borrowers/{id}/settle-splits`, `SplitService.settle`) saves an ordinary **Loans Collected income** (so collected, Receivables and balances follow with no special case) plus one `split_settlement` row per expense it cleared (oldest first, or the `expenseIds` given; at most what is open, anything else is a plain Loans Collected); `GET /api/splits` lists those rows, and the browser works out each person's rows with `personSplits` / `personPayments` from `transactions` + `splitSettlements` (state). A settled expense cannot change amount/shares or be deleted, a payment that settled shares cannot be edited, and deleting that payment frees the shares again; a person with shares cannot be removed. **Reports count the user's own share**: `rupeeTransactions()` (`core/currency.js`) maps expenses through `atOwnShare`, and the Transactions found-totals use `ownAmount`; `splitShares`, `sharedTotal`, `ownAmount` and `atOwnShare` live in `currency.js` (so tests that load it need nothing else), the rest of the maths (`computeShares`, `personSplits`, `personPayments`) in `split-calc.js`. The form's split box is `splitField` (hidden for Loans Given; money in paise so shares always add up; the odd paise stay with the user), the person's list `personTransactionsBlock` + the Settle window (`openSettleBalance`, the shared Ledger dialog) are in `split-block.js`, drawn by `personRow` in `accounts.js`. **The other direction (`V18__paid_by_person.sql`, `Transaction.paidByBorrowerId` + `ownShare`, `TransactionData` 14th/15th components, `SplitService.repay`, `POST /api/borrowers/{id}/repay-splits`)**: an expense somebody else paid has no `fromAccountId` (`TransactionService.checkPaidBy`: ordinary expense only, person on the list, `ownShare` > 0 and <= the bill, no splits as well), moves no balance, and counts at `ownShare` in the reports (`ownAmount` / `atOwnShare` in `currency.js`). What you owe is kept **apart** from what they owe you: `BorrowerView.youOwe` = sum of `ownShare` of their bills - what you paid back (`LoanService.summary`), never netted into `owed` or the Receivables total, **Receivables is the net balance**: `AccountService.listSummaries` takes `youOwe` (all bills less paid back and set off) off the Receivables total, and a person's row shows `owed - youOwe` (a negative amount when you owe them); there is no separate "You owe" line any more. **Paying back** (`SplitService.repay`) saves an ordinary **Loans Given** expense plus `split_settlement` rows to the bills it cleared; the Loans Given amounts that have such rows are *not* counted as lending (`sumRepaidByBorrower`/`sumRepaidAll` are taken off `given` in `LoanService.summary` and off `loansNet` in `AccountService.listSummaries`). The same `split_settlement` table serves both directions (its `income_transaction_id` is the payment, an income when they paid you, an expense when you paid them). A repaid bill cannot change or be deleted until the payment is. **Settle is by balance** (`SplitService.settleBalance`, `POST /api/borrowers/{id}/settle-balance` `{date, accountId, amount, note}`): what you owe each other is first set off, oldest items first, as two `split_settlement` rows per pairing with `income_transaction_id` **0** (no payment; they lower `shared` and `youOwe` equally via `sumOffsetByBorrower`/`sumOffsetAll`, are never counted as repaid, cannot be undone and keep the expense locked), The offset goes bills against open shares first, then against the plain loans (the person's whole `owed` less their open shares; those rows sit on the bill side only, and the balance falls through the same bill-side total); then `amount` (at most what is left, 0/null when the offset alone settles everything) is paid **by whoever still owes**: if they owe anything (shares or loans) it is a Loans Collected income via `collect` (cleared against their open shares first, the rest is plain loan repayment), only when you owe more is it `repay` (Loans Given). The window (`balanceOf` in `split-block.js`) works the same sums out for its text and direction. UI: `Paid by` select (inside the Split box, first under the tick box via `splitField(...).top`, shown only while it is ticked, `splitField.isOn/onToggle/showPeople`) + `Your share` in the Expense form; per person a `personToggle` arrow before the name and, when open, `personTransactionsBlock` under it (loans, shared expenses and bills newest first, a line for the person's opening amount, any write-off from `writeOffs` state (`GET /api/loans/write-offs`, shown as "Written off: reason" with its day, with a pencil (`PUT /api/loans/write-offs/{id}` `{date, note}`: day not in the future, reason required, the amount never changes) and a bin (`DELETE`, the amount is owed again; `LoanService.updateWriteOff` / `deleteWriteOff`)), then the payments and any offset) and one `settleButton` beside the name in `personRow` (`accounts.js`, whose amount is the net balance `owed - youOwe`), the window is `openSettleBalance` in `split-block.js`; `personLedger`, `ledgerBalance`, `personOffset`, `personPaidFor` in `split-calc.js`. Not yet in the Excel export/import (only a Loans sheet column) and a write-off of a person does not close their open shares (`docs/SPEC.md` 8b).
- **Deactivating and resetting.** A deactivated account allows nothing: `TransactionService.requireActive` refuses to create, change or delete a transaction that uses it and `AccountService.update` refuses it (the Edit window, `edit-account.js`, then shows only Activate and Delete); the Deactivate / Activate buttons call `POST /api/accounts/{id}/deactivate` and `/activate`. **Reset balance** (`AccountService.resetBalance(id, note)`, `POST /api/accounts/{id}/reset-balance`, window built with the shared Ledger dialog) needs an active ordinary account, a non-zero balance and a required note (at most 255 characters, what happened to the money); it writes one transaction dated today for the whole balance directly through the repository, in the fixed categories `BALANCE_ADJUSTMENT_EXPENSE` / `BALANCE_ADJUSTMENT_INCOME` (name Balance Adjustment, `SystemCategories`): an expense for an asset that holds money or a liability that was overpaid, an income for an overdrawn asset or a liability that owes. `TransactionService` refuses the category on a new transaction, the forms hide it (`ADJUSTMENT_KEYS`), and `NOT_SPENDING_KEYS` (loans and adjustments) keeps it out of Stats, Spending Review and Budgets. Refused for the Ledger, portfolios, Recurring Deposits, Jewellery, Receivables and a ring-fenced account.
- **Paying a loan or card is an expense with a to-account.** The Pay button on a Debt or Credit Card row (`js/panels/liability-payment.js`, in the transaction window) saves an EXPENSE in the fixed category Liability Payments (`SystemCategories.LIABILITY_PAYMENT`) with `fromAccountId` = a non-liability account and `toAccountId` = the liability; `TransactionService.checkPayment` enforces it and refuses a to-account on any other expense. Balances and net worth need no special case because money into a liability already lowers what is owed. `isLoanCategory` means only Loans Given/Collected (they need a `borrowerId`); the front end tells them apart with `PERSON_CATEGORY_KEYS` and `LIABILITY_PAYMENT_KEY` in `constants.js`, and `isLiabilityPayment(t)` is "an expense with a to-account". A `debt_detail` row (`DebtService`, `/api/debts`, `debtEmis` in the page) makes a Debt a fixed loan with a monthly EMI; no row means custom. The category list in the ordinary Expense form hides Liability Payments, and `charts.js` counts it as spending.
- **The Ledger is walled off from ordinary transactions.** `TransactionService` refuses any create/edit/delete touching the Ledger account. `LedgerService` writes its own transactions directly through the repository, bypassing those checks, so keep the two in step. A Ledger bucket is not an account: its balance is the sum of `ledger_entry` rows (FUND, PAY, MOVE_*, CLOSE_*, OPENING, ADJUST, INTEREST), so history is never deleted, and the buckets always sum to the Ledger account's balance. There is no "unallocated" money: the default Buffer bucket (the only buffer, not closable) absorbs extra money, interest and leftovers. `LedgerService.tidyUp` (run by `LedgerInitializer`) repairs older data at start-up.
- **Mutual Funds (and Shares) are a portfolio account.** `PortfolioService` keeps one INVESTMENT account per kind (`portfolio_detail`) whose balance is the sum of its `holding` rows' **invested amounts** (what the holdings cost, not what they are worth today; the Investments tile and net worth count the same, and the level shows the current value and the gain or loss in percent as a second, small line: `levelMarket`/`marketText` in `accounts.js`), not opening + in - out (`AccountService.listSummaries` and `NetWorthService`'s latest point both override it). Withdraw (`WithdrawRequest(toAccountId, amount, date, investedAmount)`: `amount` is the current value of what is sold, which is what arrives, and `investedAmount` its cost, so the difference is the profit; with no `investedAmount` the invested amount comes off in the same share as the value and `amount` cannot exceed the worth; a sale that fetched more than the value on file raises the value to it first) writes an ordinary transfer, changes the holding, lowers `portfolio_detail.total_invested` by the cost of what it took out and adds what it paid above (or below) that cost to `portfolio_detail.realized_gain` (V13; the card's "Profit from sales", also on the export sheet), so after everything is sold Total invested and the Difference (Total invested minus Invested) are back to 0 and the profit stays visible; Invest takes money from a bank or cash account (a transfer) and adds it to the portfolio's Total invested without touching any holding (`InvestRequest` and `WithdrawRequest` take an optional `date`, never in the future, for the transfer and the value history: the Money Manager import saves history through them); `TransactionService` refuses ordinary transactions on the account. Each holding's invested amount and current value are also saved per day in `holding_snapshot` (on add, update and withdraw) to feed the Stats line graphs (`js/panels/portfolio-stats.js`, `GET /api/portfolios/{kind}/stats`). A dividend is an ordinary income transaction with `holdingId` set (`PortfolioService.dividend`; `TransactionData` is untouched because the service writes the entity directly). Mutual Funds and Shares each have a card (`js/panels/portfolio.js`, config-driven by kind, reusing the Ledger's dialog).
- **Recurring Deposits are a walled-off investment account with a card of their own.** `RecurringDepositService` (`/api/recurring-deposits`, `js/panels/recurring-deposits.js`, tables from `V12__recurring_deposit.sql`) keeps one INVESTMENT account, "Recurring Deposits" (a row in `recurring_deposit_detail` marks it, like `portfolio_detail`; `TransactionService`, `LedgerService.fund` and `AccountService.requireManagedFieldsUnchanged` refuse it like the portfolios), and one `recurring_deposit` row per deposit: start date, term in months, optional monthly amount and yearly rate, `already_deposited` (added to the account's opening balance, as a holding already owned is), status OPEN or CLOSED and, once closed, `closed_on` and `received_amount`. **A deposit is closed, never deleted, so its history stays** (there is no delete). Deposit is a dated transfer from a bank or cash account into the account and Close is a transfer of everything deposited back out plus income for the rest (category Bank Interest, else Investment Income), all carrying `financial_transaction.recurring_deposit_id`; the account's balance is therefore just opening + in - out, and an open deposit counts at what was paid in (interest arrives when it is closed; the user chose this over accruing it). The view computes `progressPercent` (days elapsed over the term, to the closing day for a closed one), `monthsElapsed`, `maturesOn`, `plannedTotal` and `expectedMaturity` (quarterly compounding of each instalment); the card draws the bar with `.ef-bar` / `.ef-fill`, a "Transactions" fold per deposit (closed at first, its own rows via `txnRowElement`) and a "Closed" fold; a mistaken deposit into an open deposit can be removed with the bin on its row (`DELETE /api/recurring-deposits/transfers/{id}`). The Excel export has a Recurring Deposits sheet once the card is used. Never log names or amounts.
- **Jewellery is a walled-off item account.** `JewelleryService` (`/api/jewellery`, `js/panels/jewellery.js`) keeps one `JEWELLERY` account (Level 3) whose balance is the cost of its `jewellery_item` rows (no current value); an item already owned shifts the account's opening balance, one paid from a bank or cash account is a transfer, a sale is a transfer of the cost plus income or an expense for the difference. `TransactionService` refuses ordinary transactions on it, like the Ledger. `V6__jewellery.sql` added the ENUM value and the table.
- **Net worth history** (`NetWorthService`, `/api/net-worth`) replays transactions by date on top of the opening balances using the same sign rules as `AccountService.listSummaries`; keep the two in step when a balance rule changes. **Receivables is left out of net worth** (it is shown, not counted): `NetWorthService` skips RECEIVABLE accounts and `summary.js` computes the total as Assets − Debt.
- **Ring-fencing** applies only to goal funds, only once the target is reached. `TransactionService` blocks new outflows from a fenced account, and the forms disable it as a source.

when an import finishes with no problem the page opens the Calendar, with problems it stays and shows them (and an Open the calendar button), and an error from the server is shown in `#importError`. `ImportServiceTest` exports a seeded database, empties it and imports the file, one area at a time; ## Front end

No build step and no framework. The scripts have their own tests in `src/test/js` (Node's built-in runner; `harness.js` loads the real files into an isolated `vm` page with a small fake DOM, after `toClassicScript` has taken out their `import`/`export` keywords and in strict mode, so a test page shares one scope; `static-wiring.test.js` checks the page's structure: `theme.js` then the one module, every id defined, unique top-level names, no markup built from data; `module-graph.test.js` checks the imports: each resolves, names an export, is used, is not also declared inside the file, no cross-file name is used without one, and it loads the real module graph in Node). Add a test there for any new logic in `js/`; objects returned by `page.run()` are plain copies, use `page.raw()` for promises and DOM nodes. `Dashboard.html` is only a shell; `js/app.js` fetches each `panels/*.html` fragment into its `data-include` slot (fragments may nest) and then calls every `initX()`. The files are ES modules: `Dashboard.html` loads `js/core/theme.js` as a plain script in the head (it must block, so the saved theme is on the page before anything is drawn) and `js/app.js` as the one `<script type="module">`, which imports everything else, so there is no load order to keep. Each file imports what it uses and exports only what other files use. **A file cannot assign to a variable it imports**: the shared state in `core/state.js` (and `calMonth`, `calSelected`, `txnPage`) is replaced through exported setters (`setAccounts(...)`, `setTxnPage(1)`), while mutating it (`accounts.push`) and reading it are as before. Known small rough edges in the panels (none loses data) are listed in `docs/SPEC.md` section 8a, and the back end's in section 8b (read it before touching the header filter, the Ledger, account types or the log lines); check there before assuming an odd behaviour is new. Nothing imports `app.js` (a test checks it); the panels still import each other in a cycle (Accounts opens the Ledger and transaction dialogs, which redraw Accounts), which is safe because they only call each other later. Top-level names should still be unique across files, because a test page loads them into one scope.

- Shared state is exported from `js/core/state.js` (`accounts`, `transactions`, `ledger`, `emergencyFund`, `loans`, ...); a file that imports it reads it, and replaces it only through the setters at the end of that file (`setAccounts(...)`). `refreshData()` (from `core/refresh.js`, which `app.js` points at its `loadAllData` with `setRefreshHandler`, so a panel never imports `app.js`) refetches everything and calls `render()`; call it after every change instead of patching the page by hand.
- Each panel has a `renderX()` and/or an `initX()`; CSS is split to match (`css/*.css`), with every progress bar styled in `css/progress.css` and `utilities.css` loaded last.
- Use `el()` and `textContent` for anything that comes from the database, never string-built `innerHTML`.

The shared date range (`js/panels/period-filter.js`; Today, From, To and Clear in the `#wsRange` row at the top of the view card) scopes the whole dashboard: `renderPeriod()` redraws the calendar's range, the net worth line, the accounts' stats, the pie charts and the transactions from it, and `periodMonthKeys(firstKey, cap = 60)` gives the months any line graph should cover (the net worth graph passes 120). There is no separate period panel. Stats does not use it: the Stats view has its own Weekly / Monthly (default) / Annually / Period buttons (`js/panels/stats-period.js`: `statsRange()`, `statsInPeriod()`, `statsMonthKeys()`, arrows via `statsStep()`), and `charts.js` calls those instead of `inPeriod` and `periodMonthKeys`; the category line graph spans at least the 12 months ending with the period, but never starts before the first month that has data for the chosen category (`categoryMonths` in `charts.js`), so it can be shorter.

The view card (`panels/workspace.html`, `workspace.js`), the main part of the page under the header, flips between faces. Seven tab buttons (Calendar, Transactions, Budgets, Spending Review, Stats, Accounts, Net worth) and, in the menu's Organiser group (`.menu-view` buttons with `data-view`), Reminders and Notes (`showWorkspaceView` marks the pressed item and the menu button's `.in-use`) pick the view and every change turns the card: the view on show is on one face, the next is moved onto the other from `#wsHolder` before the turn, and the old one goes back afterwards. The net worth figures are built by `buildNetWorthFigures` in `summary.js` as a sum (Assets, − Debt, a rule, then the total as a bold number with no label, all right-aligned, with Receivables on its own grey line below marked "not counted"; `nwFigures.assets` leaves out Receivables, with a fold-out of Assets by kind of account (`nwParts`, `paintParts`, starts hidden; amounts use `rupees2`, always two decimals, so the digits line up) that adds up to Assets, while the server's net-worth series and the graph's table still count receivables in "Assets (with receivables)") into `#nwFigures` above the graph in the Net worth view (there is no net worth card at the top any more) and found by `.js-nw-*` classes, not ids. The graph (`net-worth.js`) shows the last `nwZoom` months (1Y default, 3Y, 5Y, All) of the months the shared range allows; `refreshData` asks for 120 months and the server returns at most 60. More than `NW_MAX_POINTS` (36) months are drawn as quarter-end points by `quarterly()` while `netWorthSummary()` and the table still use every month, and the table is a `<details>` per year. All four figures start masked; the single eye at the view's top right (`#nwEye`) shows or hides them together. The Accounts view is a wall of coloured level tiles (`renderAccounts` in `accounts.js`: name, total, account count; colour from `.level-N`); clicking one sets `openLevel`, renders that level's cards and rows into `#levelBody` and turns the card to the `level` view (`showWorkspaceView("level")`, under the Accounts button), with a back button to the tiles. `renderLevelBody` is the old per-level group code. Views are plain fragments (`calendar`, `transactions`, `budgets`, `insights`, `charts`, `accounts`, `net-worth`, `notes`, `reminders-view`) with no card chrome of their own; Calendar is shown first. `WS_NO_RANGE` in `workspace.js` hides the date range row on Accounts, the level view, Notes, Reminders, Stats, Spending Review and Budgets (Stats has its own period; the other two work by month); `WS_NO_ADD` hides the red + on Net worth, Stats, Reminders, Spending Review and Budgets.

**Calendar heatmaps**: `calMode` ("calendar" | "expense" | "income", buttons `#calModeCalendar` / `#calModeExpense` / `#calModeIncome`, not saved) recolours the same grid. The pure maths is `calendar-calc.js` (`monthHeat` per-day totals, counts, averages and levels from `rupeeTransactions()` without transfers, Loans Given/Collected and adjustments, `heatLevelOf` levels from a score that is half the day's rank among the active days and half its size against the month's biggest day (so Rs 699, Rs 30,000 and Rs 60,000 are different levels), with no rupee thresholds, `heatSummary`, `heatText`); `calendar.js` only draws (`.heat-expense` / `.heat-income` + `.heat-l0`..`.heat-l4`, `describeHeatDay` for the aria-label and the shared tooltip, `renderHeatSummary`, arrow-key focus). The colours are the `--heat-e0..4` / `--heat-i0..4` variables and their text colours `--heat-et*` / `--heat-it*` in `css/base.css` for light and dark (`dark-theme.test.js` checks the light values and the 4.5:1 text). The Calendar (`js/panels/calendar.js`) keeps its own month with ‹ › but follows the shared range: setting a range jumps to its month (`calendarFollowPeriod`), highlights the days in it and adds a second In / Out / Net line for a From / To range, not for Today (the first line is always the month shown). The red round + (`#calAdd`, far right of the `#wsRange` row, shown on Calendar and Transactions only; `WS_NO_RANGE` and `WS_NO_ADD` in `workspace.js` say which views hide the row and the +) opens a new Expense with `openTransaction("EXPENSE", null, calSelected)`; the form itself has the Income | Expense | Transfer buttons (`#txnKinds`, `showTxnKinds`, `switchTxnKind` in `transaction-form.js`; only for a new transaction, hidden when editing and in the Pay window), which keep the date and amount typed. It reuses `txnRowElement` from `transactions.js` for a chosen day's rows and projects Ledger payment dates from each bucket's `nextPaymentDate` and `frequencyMonths`. A day's cell also shows the titles of its open one-off reminders as draggable `.cal-chip`s (`CAL_CHIPS` = 2, then `.cal-more`) that can be dropped on another day.

Loan rows. A Debt row has a repayment bar and line like a card's usage bar (`loanProgress` in `loan-calc.js`, pure: the whole loan is its opening amount plus what was borrowed on it since, repaid = every payment into it, left = the balance, percent, EMIs to go at the fixed EMI with interest not counted; 100% and green once nothing is owed, and then the loan is **closed**: `loanClosed(a)` in `accounts.js` greys the row green, shows "Closed" for the amount and "· closed" in the type line and drops the Pay button; history stays and a card at zero is never closed), and a fold "Transactions (n) ▸" under it (`loanTransactionsBlock` in `loan-block.js`: closed at first, then the loan's own rows newest first through `txnRowElement`, paged 10/25/50/100 like the Transactions list; `accountRow` in `accounts.js` adds it to the `.account-block` as it does `cardCyclesBlock` for a card).

Credit card cycles. `card-cycles-calc.js` (pure) works out a card's cycles from `cardStatementDays`/`cardDueDays` (`cardCycles`: a cycle is [one statement date, the next), a transaction on the statement day is in the next cycle like `cardStatementAmount`; the bill state `paid`/`part`/`due`/`overdue`/`none` counts payments from the statement day to the due day; no statement day = calendar months), `card-cycles.js` draws the fold `cardCyclesBlock(card, redraw)` that `accountRow` in `accounts.js` adds to the `.account-block` of every CREDIT_CARD row: one cycle at a time with ‹ dates › paging (`cyclePage`, 0 = the running cycle, kept per card until reload; `blocksOpen` for the fold; reuses `txnRowElement`); the cycle's rows are paged like the Transactions list (`transactionsOf`: `rowsPerPage` 10/25/50/100 shared by all cards, `rowsPage` per card and cycle, chips `rowsShown` All / Spent / Paid into the card, the `.pager` classes of transactions.css). Nothing in the Transactions view changes.

Running balance in a row. `accountCell` in `transactions.js` puts a `.sub` line under the account of every row: "<account> remaining balance ₹X" for each account on either side (so a transfer has two), "remaining owed" for a DEBT, and for a CREDIT_CARD "remaining balance" (limit less owed) or "withdrawal" (no limit). `balanceAfter(t, accountId)` works all of them out in one date-then-id pass per load (opening balance + in − out, fees on the from side; liabilities flip the sign) and caches by the identity of `transactions` and `accounts`; RECEIVABLE, Jewellery and portfolio accounts are skipped because their balance does not come from transactions. Keep it in step with `AccountService.listSummaries`.

Transaction search. It is entirely in the browser, because the whole list is already loaded: `txnQuery` (words, category, account, min, max) is applied by `txnMatchesQuery()` in `transactions.js` together with the kind chips and the shared date range. Each transaction's search text is built once (`txnHaystack`, cached in a `WeakMap`; a refresh brings new objects, so it never goes stale) and avoids `toLocaleString`/`formatDate`, which made a search over 10,000 transactions take 590 ms instead of 24 ms (5 ms after the first). If you add a field to a transaction that should be findable, add it to `txnHaystack`.

Jump and export. `showTransactionsFor({account, category, kind, from, to})` (`transactions.js`) sets `txnQuery`/`txnFilter`, calls `setSharedRange` (`period-filter.js`, replaces the shared range, so the Stats period carries over) and switches to the Transactions view; account rows (`accountRow`) and the Stats drill-down (`renderDonut`, from `statsRange()`) call it. `visibleTransactions()` is the one definition of what the list stands for and feeds both the list and `exportTransactions()`/`transactionsCsv()`; `csvCell` quotes cells and prefixes `'` to ones starting `= + - @ tab CR` (formula injection). Keep the BOM.

Theme and reminders. There are three themes, `data-theme` = `light`, `dark` or `color`, chosen with the buttons `#theme-light`, `#theme-dark`, `#theme-color` in the menu; `css/color-theme.css` (after `base.css`) overrides only bg, surface, muted, accent, accent-fill, border and tint for Color, so keep chart, status and fill colours out of it (`dark-theme.test.js` checks its contrast). `js/core/theme.js` is loaded in the `<head>` (first script, so the saved theme is on the page before anything is drawn); it sets `data-theme` on `<html>` from `localStorage["theme"]`, else the computer's setting, and `initTheme()` wires the header button. All colours are CSS variables: `:root` in `css/base.css` for light, `:root[data-theme="dark"]` for dark (chart colours in `css/charts.css`). Text colours get lighter in dark but **solid fills under white text use `--accent-fill`, `--green-fill`, `--red-fill`** (the same dark values in both themes); use those for any new filled button or badge, and `--series`, `--series-div`, `--series-value`, `--series-invested`, `--axis`, `--track-*`, `--tint` for graph and track colours, never a hex value (`--series-value` and `--series-invested` colour the Mutual Funds / Shares graphs, set in `base.css` for light and dark, so they work outside a `.chart-card`). `dark-theme.test.js` fails if a variable is added to light and forgotten in dark, if text/fills drop below 4.5:1, or if the dark chart colours change from the five that passed the data-viz validator on `#171d26`. **Class names are global across the css files**: `.cat-row` is both the Edit categories dialog's flex row (`categories.css`) and the Stats / Net worth table row, so `charts.css` resets `.chart-table tr.cat-row` to `display: table-row` (a test guards it); check `grep` for a class name across `css/` before reusing one. a card's bill in Coming up is `statementDue()` in `reminders.js` when the card has a statement day (owed on the last statement before the due date, less payments into the card since, capped at the current balance; nothing is listed when that statement is still in the future), else the whole balance; `cardStatementDays` in `state.js` mirrors `cardDueDays`; `js/panels/reminders.js` builds the "Coming up" section, three panels in `#remindersBar` (in `Dashboard.html` after the header, in this order: `#backupBanner`, then `#remindersBar`, then the view card, so the title comes first) (`PANELS`: Bills = cards and Ledger, Reminders = your one-off ones with tick box and Tomorrow, Recurring = repeating ones; a fourth, **Done recently**, is built separately by `recentlyDone()`: one-off reminders with `done`, a `doneOn` and their own `date` both within `DONE_DAYS` (7), newest first, `DONE_SHOWN` (5) rows plus a "+ N more" note, each row a `reminderCheckbox` ticked (unticking is the ordinary `PUT /{id}/done`), and it keeps the section visible even when nothing is coming up; a panel with no items is not built; a row is a `button.reminder-item` with `.ri-main`, `.ri-detail`, `.ri-when` and an `aria-label` of the full sentence from `reminderText`), from `accounts` (+ `cardDueDays`, from `credit_card_detail.due_day`) and `ledger.buckets`; `calendar.js` `calendarDue()` marks the same payments.

Motion. `css/motion.css` (loaded just before `utilities.css`) holds the timing variables (`--motion-fast`, `--motion-base`, `--motion-slow`, `--ease-out`) and the animations not tied to one panel: dialogs and the lock overlay fade in (they are shown by removing `.hidden`, which restarts the animation; there is no fade-out), press feedback on `.btn`, `.chip`, `.icon-btn` and `.level-tile`, the `.rise` entrance and the Stats ring (`.donut.sweep`: a `.donut-trace` circle is drawn round first, then each `.slice` swells out in turn, `--i` is its place, then the labels fade in; `renderDonut` always draws it, so a period change or coming back from a slice replays it, and `showWorkspaceView("stats")` replays it with `replay(ring, "sweep")` on opening Stats; unlike the bars it is not `growsOnce`, so a redraw while Stats is on show also replays it). **Every animation must sit inside `@media (prefers-reduced-motion: no-preference)`.** A new row, card or tile gets `riseOnce(node, key)` (from `util.js`; it uses `growsOnce`, so a redraw does not replay it, and the key must be stable, such as the row's id); a test that finds rows by exact `className` must allow the extra `rise` class. The net worth figures use `countTo(node, from, to, format)` and `stopCount(node, text)` (`summary.js`): the real digits are never put on screen while amounts are hidden, and with no `requestAnimationFrame` (a test page) or reduced motion the end value is set at once. More helpers in `util.js`: `replay(node, class)` restarts a CSS animation class (the new view gets `.view-in` in `showWorkspaceView`, the calendar grid `.slide-next`/`.slide-prev`); `setBarWidth(fill, key, pct)` replaces `fill.style.width = ...` for every progress bar and adds `.shift` (reading `--from`) when the same bar comes back with a different value, so use it for any new bar; `flashOnNext(key)` before a redraw plus `takeFlash(key)` in the row builder gives a saved transaction row `.flash` (a row that rises does not flash; the save handlers call it with the returned id); `collapseOut(selector)` lets rows marked `data-txn-id` fold away before `refreshData()` in the delete handler. The level tiles' totals count up with `countTo` (`tileTotals` in `accounts.js`). Chart draw-ins and progress bars keep their animations in their own css files.

Categories page. Categories is a view of the view card, not a popup: the menu item `#editCategoriesButton` (Categories > Edit / Add categories) has `.menu-view` and `data-view="categories"`, so `initWorkspace` turns the card to `#categoriesView` (`panels/categories.html` in the holder, `showWorkspaceView("categories")` calls `showCategories()`; it hides the date row and the red + like Notes, `WS_NO_RANGE` and `WS_NO_ADD`). `renderCategories()` (also called by `render()` in app.js) draws Expense / Income tabs with counts and a plain list (a row per category, its sub categories indented under it, the buttons on the right of each row, as in the old popup), and beside each name how many transactions use it (a category counting its sub categories'); the fixed ones (Loans Given / Collected, Liability Payments) are locked.
